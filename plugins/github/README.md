# GitHub

A right-sidebar panel with the issues, pull requests and Actions runs of the focused workspace's repo. Every GitHub call goes through the `gh` CLI already logged in on the machine; the plugin stores no tokens. The panel (`src/panel.tsx`) asks with `plugin.request`, the plugin's own worker (`src/worker.ts`) answers with `orca.panels.handle` and runs `gh`; `src/protocol.ts` types both sides. Orca transpiles both files when they load, so there is no build step: save and the panel or worker reloads.

## Panel

Tabs Issues | Pull requests | Actions, each with its own search, filters, order, page and open row. A list takes the panel's height and shows GitHub's page of 30 rows, with Previous / Next pinned under it; GitHub's search stops at 1,000 results (so does the runs list once a filter is set), and the page line says so. Issues and pull requests show their open and closed counts beside Open and Closed, counted when the list starts over, not on every page; All lists both. The filter button opens author, assignee (a login or `@me`) and label (workflow, status, event and branch for runs) and shows how many are on; the sort button opens newest, oldest, recently updated and most commented (runs have no order to choose). A pull request opens a short detail, and Back returns to the list.

An issue opens as GitHub shows it: state, labels, assignees and milestone, the body, then its timeline of comments, "mentioned this" (another issue or pull request that links here: an issue of this repo opens in the panel, anything else on GitHub) and closed or reopened events. A long timeline shows its first 30 and latest 10 items with Load more between. `#12` and `owner/repo#12` in text are links; images only show on GitHub (panel Markdown loads no remote images), and text past the panel's message limit is cut with a link to the rest. From the detail: comment (Cmd+Enter), edit or delete any comment GitHub lets you, close as completed, not planned or a duplicate (asked first; with text in the box it is Close with comment), reopen, edit the title and body, pick labels and assignees, and react (the ☺ + strip offers GitHub's eight). New issue (+) opens a form with title, body, labels and assignees, then the new issue. When the Issues tab shows a workspace, it opens what that workspace showed last in this panel run (an issue or the list); the first time, the issue Orca links to the workspace (one made from an issue), or the list when there is none. Back and tab switches stay put. Back reloads the list after a change. Refresh asks for the repo again and reloads the page on screen; Open on GitHub opens the tab's page of the repo, or the open row. A state shows as a tinted glyph (Orca tones, so it follows the theme): open green, done and merged in the text colour, not planned, draft, cancelled and skipped grey, closed and failed red, running and waiting amber.

The Actions tab starts on the runs of the focused workspace's branch (every event, newest first; `N runs on <branch>`), with All branches one press away and Only <branch> to come back; a branch filter or `branch:` in the search wins. A run opens with its state, workflow and attempt, what started it, its jobs (each opens its steps with their state and time, View log once the run is done, and Log on GitHub) and, when it failed, its failed steps' logs already open; a failed job whose log gh could not read is named with the reason, beside the others. Logs keep each step's last lines so a whole answer stays under the panel's 256 KiB message limit, say how many lines they show, and link to the full log on GitHub. A run that is done offers Re-run failed jobs and Re-run all jobs, then waits for the new attempt (GitHub starts it a moment later); one still going offers Cancel run (asked first) and is live: the worker reads it every 5 s and posts `run.progress` to the panel, and the list row follows. Leaving the run or closing the panel stops it. Run workflow (▶ on the Actions toolbar) opens a form: the workflow (the filtered one, else the first), the branch or tag to read it from and run it on (the workspace's branch when GitHub has it, else the default branch), and its `workflow_dispatch` inputs by type (text, switch, choice, environment). A branch typed in the box is read on Enter, and Run waits for it. A workflow without that trigger says so; a file the panel cannot read gets name and value rows instead.

## Files

- `src/protocol.ts`: the requests `repo.get`, `repo.pick`, `repo.unpick`, `issues.list`, `pulls.list`, `runs.list`, `labels.list`, `workflows.list`, `assignees.list`, `repo.links`, `issue.get`, `issue.timeline`, `issue.comment`, `comment.edit`, `comment.delete`, `issue.close`, `issue.reopen`, `issue.edit`, `issue.create`, `reaction.set`, `run.get`, `run.logs`, `run.rerun`, `run.cancel`, `run.watch`, `workflow.form`, `workflow.run` and the events `repo.changed` and `run.progress`. Every answer is `Answer<T>`: `{ ok: true, ... }` or `{ ok: false, error: { code, message } }`, since a thrown code would reach the panel only as `action_failed`.
- `src/gh.ts`: `runGh(args, { cwd, signal, json, timeoutMs, maxBuffer })` runs `gh` and throws a `GhError` whose `code` the panel can explain. Handlers take it injected, so tests never call real GitHub.
- `src/exec.ts`: `run` (child processes, with the user's PATH first), `terminalPath` (the folder a terminal runs in) and `workspaceLinks` (the issue and pull request Orca links to a workspace, from `orca worktree show --json`; host API has neither), both from the Orca CLI and null on any failure, as its JSON is not part of the plugin contract. The CLI is looked for in the macOS app bundle, then as `orca` on PATH; on Linux and Windows only PATH is tried, so without `orca` on PATH a terminal never breaks a tie and the panel asks for a pick instead.
- `src/focus.ts`: finds the focused workspace's folder. `workspace.readContext` gives only a branch and a name, so it matches them against `workspace.list`, and when that is not one workspace (root clones are named after their branch, so every repo on `main` looks alike) it asks which folder a focused terminal runs in, since that terminal belongs to the focused workspace, and when none tells it uses the folder the person picked for that branch and name (kept in storage under `picks`, shared by every clone with that branch and name, used while it still matches, forgotten with Change workspace). With neither, the panel lists the candidates to pick from.
- `src/repo.ts`: `gh repo view --json nameWithOwner,url` in that folder, and the tracker behind `repo.get`: it follows `workspace.changed`, keeps a found repo per folder, asks again after an error, and posts `repo.changed` to open panels when the answer changes.
- `src/lists.ts`: one page per request. Issues and pull requests go through GitHub's GraphQL search (`repo:o/r is:issue is:open author:… label:… sort:created-desc <words>`), which pages by cursor and, when asked, counts open and closed in the same call. Runs go through the REST `actions/runs` API, paged by number, narrowed to the workspace's branch (`git rev-parse` in its folder) when `scope` is `branch`; it has no word search, so the runs search takes qualifiers only: `branch:`, `status:`, `actor:`, `event:`, `workflow:` (an id, a file name, or a workflow name looked up first; quote a name with spaces). Also the repo's label names and workflows, for the filters.
- `src/issues.ts`: one issue. Reads through GraphQL: the issue with its reactions and both ends of its timeline (`timelineItems` first 30 and last 10, comments, cross-references, closed and reopened), then later pages by cursor; each body is cut to fit and a page ends early once its comments fill their share of the 256 KiB message limit. Writes through gh's issue commands (`gh issue comment`, `close --reason`/`--duplicate-of`, `reopen`, `edit --add-label`…, `create`), which take label and login names; comments are edited and deleted through the REST API by id, reactions through GraphQL `addReaction`/`removeReaction` by node id (the REST API needs the reaction's own id to remove it).
- `src/runs.ts`: one run. The run and the jobs and steps of its latest attempt through the REST API; logs of a finished run through `gh run view --job N --log-failed` per failed job (at most 5, as Orca's Checks panel reads; gh reads one job's log in about a second, a whole run's in tens; a job that fails is named, the others still show) or `--log` for one job, with a 60 s limit and a 64 MiB buffer; a run too big for one message drops the steps of passed jobs, then all steps; `gh run rerun [--failed]`, `gh run cancel`; `run.watch`, which holds up to 100 s, reads the run every 5 s and posts it to the panel that asked until it is done (with `attempt`, until that attempt is) or the panel stops waiting; and the Run workflow form (`gh workflow view --yaml --ref`, the repo's environments) and `gh workflow run --ref -f name=value`.
- `src/logs.ts`: gh's log lines cut into steps, without timestamps, colour codes or group and action markers, and trimmed to the end of each step within one budget.
- `src/workflow-inputs.ts`: the `on:` block of a workflow file read for `workflow_dispatch` and its inputs. The plugin carries no YAML library, so it reads the plain YAML these blocks are written in and gives up (inputs null) on anchors, flow mappings or values over several lines.
- `src/look.ts`: glyph, tone and words for each state, timeline event, reaction and error code.
- `src/refs.ts`: turns `#12` and `owner/repo#12` into Markdown links, leaving code, links and URLs alone.
- `src/store.ts`: the panel's atoms and actions: the selected tab, and per tab the search, open/closed/all, filters, order, counts, a stack of page cursors and the open row; label, workflow and assignee choices.
- `src/issue-store.ts`: the open issue, its timeline pages, what is being typed, and every write; one write at a time, and the issue is asked for again after it, except comment edits, deletes and reactions, which change in place.
- `src/run-store.ts`: the open run, its open job and log, its writes and its watch (aborted when the run is left), and the Run workflow form.
- `src/views.tsx`, `src/issue-view.tsx`, `src/issue-forms.tsx`, `src/run-view.tsx`, `src/parts.tsx`, `src/panel.tsx`: the components.
- `src/panel.check.ts`: `orca plugin check` scenarios, with the worker stubbed: no workspace, several workspaces to pick from, not a GitHub repo, gh logged out, empty repo, rate limited, each tab with rows, runs with one queued and, through a workspace linked to issue 120, an issue open, closed, with a long timeline, read only and not found.

Error codes: `no_workspace`, `workspace_not_found`, `ambiguous_workspace` (with `candidates`), `remote_workspace`, `host_failed`, `not_a_repo`, `gh_missing`, `gh_logged_out`, `not_found`, `rate_limited`, `timeout`, `cancelled`, `bad_query`, `gh_failed`.

## Develop

```sh
orca plugin types .        # typings into .orca/types/, needed before tsc
orca plugin validate .
orca plugin test .         # GH_LIVE=1 also runs src/repo.test.ts against the real gh
orca plugin check .
npm install && npx tsc -p .
orca plugin dev watch .    # loads this folder into Orca and prints its logs and reloads; Ctrl-C unloads it
orca plugin dev request . issues.list --data '{"state":"open","query":"","after":null}'
```

Orca names the publisher after where the plugin is installed from: the GitHub or GitLab owner of
its repository, or `local` for a folder. See
https://github.com/stablyai/orca/blob/main/docs/reference/plugin-authoring.md.
