# GitHub

A right-sidebar panel with the issues, pull requests and Actions runs of the focused workspace's repo. Every GitHub call goes through the `gh` CLI already logged in on the machine; the plugin stores no tokens. The panel (`src/panel.tsx`) asks with `plugin.request`, the plugin's own worker (`src/worker.ts`) answers with `orca.panels.handle` and runs `gh`; `src/protocol.ts` types both sides. Orca transpiles both files when they load, so there is no build step: save and the panel or worker reloads.

## Panel

Tabs Issues | Pull requests | Actions, each with its own search, filters, order, page and open row. A list takes the panel's height and shows GitHub's page of 30 rows, with Previous / Next pinned under it; GitHub's search stops at 1,000 results (so does the runs list once a filter is set), and the page line says so. Issues and pull requests show their open and closed counts beside Open and Closed, counted when the list starts over, not on every page; All lists both. The filter button opens author, assignee (a login or `@me`) and label (workflow, status, event and branch for runs) and shows how many are on; the sort button opens newest, oldest, recently updated and most commented (runs have no order to choose). Pull requests also filter by review requested from you and by draft or ready. A run opens a short detail, and Back returns to the list.

An issue opens as GitHub shows it: state, labels, assignees and milestone, the body, then its timeline of comments, "mentioned this" (another issue or pull request that links here: an issue of this repo opens in the panel, anything else on GitHub) and closed or reopened events. A long timeline shows its first 30 and latest 10 items with Load more between. `#12` and `owner/repo#12` in text are links; images only show on GitHub (panel Markdown loads no remote images), and text past the panel's message limit is cut with a link to the rest. From the detail: comment (Cmd+Enter), edit or delete any comment GitHub lets you, close as completed, not planned or a duplicate (asked first; with text in the box it is Close with comment), reopen, edit the title and body, pick labels and assignees, and react (the ☺ + strip offers GitHub's eight). New issue (+) opens a form with title, body, labels and assignees, then the new issue.

A pull request opens the same way, with what only it has: `base ← head` (`owner:branch` from a fork), its review decision, whether it can merge (ready, conflicts, behind the base, blocked, checks not passing, draft, still checking), the reviewers still asked, and the checks of its head commit under a summary such as "1 failing · 2 pending · 4 passed" (open when one fails; each check opens its run). Its timeline adds reviews (approved, requested changes, reviewed, dismissed, with a link for the comments they left on the diff, which the panel does not show) and the merge. From the detail: comment, edit and delete comments, react, edit the title, body, labels and assignees, Review… (Comment, Approve or Request changes, with the comment box's text as the review; only an approval may be empty, and on your own pull request only a comment is offered), and Close… or Reopen…, both asked first, with the typed text as a comment. A mention of an issue or pull request of this repo opens it in its tab.

When the Issues or Pull requests tab shows a workspace, it opens what that workspace showed last there in this panel run (an issue or pull request, or the list); the first time, the issue or pull request Orca links to the workspace (one made from it), or the list when there is none. Back and tab switches stay put. Back reloads the list after a change. Refresh asks for the repo again and reloads the page, issue or pull request on screen; Open on GitHub opens the tab's page of the repo, or the open row. A state shows as a tinted glyph (Orca tones, so it follows the theme): open green, done and merged in the text colour, not planned, draft, cancelled and skipped grey, closed and failed red, running and waiting amber.

## Files

- `src/protocol.ts`: the requests `repo.get`, `repo.pick`, `repo.unpick`, `issues.list`, `pulls.list`, `runs.list`, `labels.list`, `workflows.list`, `assignees.list`, `repo.links`, `issue.get`, `issue.timeline`, `issue.comment`, `comment.edit`, `comment.delete`, `issue.close`, `issue.reopen`, `issue.edit`, `issue.create`, `reaction.set`, `pull.get`, `pull.timeline`, `pull.comment`, `pull.edit`, `pull.close`, `pull.reopen`, `pull.review` and the event `repo.changed`. Every answer is `Answer<T>`: `{ ok: true, ... }` or `{ ok: false, error: { code, message } }`, since a thrown code would reach the panel only as `action_failed`.
- `src/gh.ts`: `runGh(args, { cwd, signal, json })` runs `gh` and throws a `GhError` whose `code` the panel can explain. Handlers take it injected, so tests never call real GitHub.
- `src/exec.ts`: `run` (child processes, with the user's PATH first), `terminalPath` (the folder a terminal runs in) and `workspaceLinks` (the issue and pull request Orca links to a workspace, from `orca worktree show --json`; host API has neither), both from the Orca CLI and null on any failure, as its JSON is not part of the plugin contract. The CLI is looked for in the macOS app bundle, then as `orca` on PATH; on Linux and Windows only PATH is tried, so without `orca` on PATH a terminal never breaks a tie and the panel asks for a pick instead.
- `src/focus.ts`: finds the focused workspace's folder. `workspace.readContext` gives only a branch and a name, so it matches them against `workspace.list`, and when that is not one workspace (root clones are named after their branch, so every repo on `main` looks alike) it asks which folder a focused terminal runs in, since that terminal belongs to the focused workspace, and when none tells it uses the folder the person picked for that branch and name (kept in storage under `picks`, shared by every clone with that branch and name, used while it still matches, forgotten with Change workspace). With neither, the panel lists the candidates to pick from.
- `src/repo.ts`: `gh repo view --json nameWithOwner,url` in that folder, and the tracker behind `repo.get`: it follows `workspace.changed`, keeps a found repo per folder, asks again after an error, and posts `repo.changed` to open panels when the answer changes.
- `src/lists.ts`: one page per request. Issues and pull requests go through GitHub's GraphQL search (`repo:o/r is:issue is:open author:… label:… sort:created-desc <words>`), which pages by cursor and, when asked, counts open and closed in the same call. Runs go through the REST `actions/runs` API, paged by number; it has no word search, so the runs search takes qualifiers only: `branch:`, `status:`, `actor:`, `event:`, `workflow:` (an id, a file name, or a workflow name looked up first; quote a name with spaces). Also the repo's label names and workflows, for the filters.
- `src/timeline.ts`: what issues and pull requests share in the worker: both ends of a timeline in one GraphQL query (`timelineItems` first 30 and last 10), later pages by cursor, each body cut to fit and a page ended early once its comments and reviews fill their share of the 256 KiB message limit.
- `src/issues.ts`: one issue. Reads through GraphQL: the issue with its reactions and its timeline (comments, cross-references, closed and reopened). Writes through gh's issue commands (`gh issue comment`, `close --reason`/`--duplicate-of`, `reopen`, `edit --add-label`…, `create`), which take label and login names; comments are edited and deleted through the REST API by id, reactions through GraphQL `addReaction`/`removeReaction` by node id (the REST API needs the reaction's own id to remove it).
- `src/pulls.ts`: one pull request. Reads through GraphQL: its refs, `mergeable` and `mergeStateStatus`, `reviewDecision`, review requests, the head commit's `statusCheckRollup` (check runs and commit statuses, at most 100) and its timeline (comments, reviews, cross-references, closed, reopened, merged). A pending review (the viewer's draft) and the close that a merge makes are left out, and the timeline's size is its `filteredCount`, as `totalCount` ignores `itemTypes` on a pull request. Writes through `gh pr comment`, `edit`, `close --comment`, `reopen --comment` and `review --approve|--request-changes|--comment --body`.
- `src/look.ts`: glyph, tone and words for each state, timeline event, reaction and error code.
- `src/refs.ts`: turns `#12` and `owner/repo#12` into Markdown links, leaving code, links and URLs alone.
- `src/store.ts`: the panel's atoms and actions: the selected tab, and per tab the search, open/closed/all, filters, order, counts, a stack of page cursors and the open row; label, workflow and assignee choices.
- `src/thread-store.ts`: an open issue or pull request (a thread), one per tab: its timeline pages, what is being typed, and every write both share; one write at a time, and the thread is asked for again after it, except comment edits, deletes and reactions, which change in place. `src/issue-store.ts` adds closing with a reason and the new issue form, `src/pull-store.ts` the review and the asked close or reopen.
- `src/views.tsx`, `src/thread-view.tsx` (posts, reactions, the timeline, metadata lines and pickers), `src/issue-view.tsx`, `src/issue-forms.tsx`, `src/pull-view.tsx`, `src/parts.tsx`, `src/panel.tsx`: the components.
- `src/panel.check.ts`: `orca plugin check` scenarios, with the worker stubbed: no workspace, several workspaces to pick from, not a GitHub repo, gh logged out, empty repo, rate limited, each tab with rows; through a workspace linked to issue 120, an issue open, closed, with a long timeline, read only and not found; through one linked to pull request 131, a pull request with failing checks and reviews, your own, ready to merge, with conflicts, a draft without checks, closed, merged and not found. Scenarios cannot press, so reviews, closing and reopening are covered by `src/pull-view.test.tsx`.

Error codes: `no_workspace`, `workspace_not_found`, `ambiguous_workspace` (with `candidates`), `remote_workspace`, `host_failed`, `not_a_repo`, `gh_missing`, `gh_logged_out`, `not_found`, `rate_limited`, `timeout`, `cancelled`, `bad_query`, `gh_failed`.

## Develop

```sh
orca plugin types .        # typings into .orca/types/, needed before tsc
orca plugin validate .
orca plugin test .         # GH_LIVE=1 also runs src/repo.test.ts against the real gh
orca plugin check .
npm install && npx tsc -p .
orca plugin dev watch .    # loads this folder into Orca and prints its logs and reloads; Ctrl-C unloads it
orca plugin dev request . issues.list --data '{"state":"open","query":"","after":null}'
```

Orca names the publisher after where the plugin is installed from: the GitHub or GitLab owner of
its repository, or `local` for a folder. See
https://github.com/stablyai/orca/blob/main/docs/reference/plugin-authoring.md.
