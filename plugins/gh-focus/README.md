# gh Focus

For GitHub repos: the issue, pull request and Actions runs of the workspace you're in, beside your code. Read, comment, review and rerun without leaving the editor for the Tasks page. Not affiliated with GitHub.

Small and focused on the work at hand: the everyday reading, answering and reviewing happens beside the code. The detail work (merge, reviewers, the files diff, Projects) stays on Orca's Tasks page and pull request page, and the panel hands off to them. The Pull requests tab shows only the workspace's pull request and hands the repo's list to Orca's Tasks page; the Issues tab still lists the whole repo for now, and #22 shrinks it to a picker for the work at hand.

A right-sidebar panel with the issues, pull requests and Actions runs of the focused workspace's repo. Every GitHub call goes through the `gh` CLI already logged in on the machine; the plugin stores no tokens. The panel (`src/panel.tsx`) asks with `plugin.request`, the plugin's own worker (`src/worker.ts`) answers with `orca.panels.handle` and runs `gh`; `src/shared/protocol.ts` types both sides. Orca transpiles both files when they load, so there is no build step: save and the panel or worker reloads.

## Panel

Tabs Issues | Pull requests | Actions. Issues and Actions each have a list with its own search, filters, order, page and open row. A list takes the panel's height and shows GitHub's page of 30 rows, with Previous / Next pinned under it; GitHub's search stops at 1,000 results (so does the runs list once a filter is set), and the page line says so. Issues show their open and closed counts beside Open and Closed, counted when the list starts over, not on every page; All lists both. The filter button opens author, assignee (a login or `@me`) and label (workflow, status, event and branch for runs) and shows how many are on; the sort button opens newest, oldest, recently updated and most commented (runs have no order to choose).

An issue opens as GitHub shows it: state, labels, assignees and milestone, the body, then its timeline of comments, "mentioned this" (another issue or pull request that links here: an issue of this repo opens in the panel, anything else on GitHub) and closed or reopened events. A long timeline shows its first 30 and latest 10 items with Load more between. `#12` and `owner/repo#12` in text are links; images only show on GitHub (panel Markdown loads no remote images), and text past the panel's message limit is cut with a link to the rest. From the detail: comment (Cmd+Enter), edit or delete any comment GitHub lets you, close as completed, not planned or a duplicate (asked first; with text in the box it is Close with comment), reopen, edit the title and body, pick labels and assignees, and react (the ☺ + strip offers GitHub's eight). New issue (+) opens a form with title, body, labels and assignees, then the new issue.

The Pull requests tab has no list: it shows the focused workspace's pull request, the one Orca links to the workspace (made from it, or in Orca) or else the one gh finds for its branch (opened with `gh pr create` or on GitHub), and says when the branch has none, with Tasks and Open on GitHub. Tasks opens Orca's Tasks page, which lists, searches and filters the repo's pull requests (Orca's command takes no repo, so the page opens with its own repo selection); Orca's own pull request views close, reopen and merge. A pull request opened from a mention has ← Back to the workspace's own. It reads like an issue, with what only it has: `base ← head` (`owner:branch` from a fork), and in Orca's own words and counting, so it reads like Orca's Checks tab: its review decision (Approved, Changes requested, Approval required; no line when none is needed), whether it can merge (Able to merge, Conflicts, Behind, Blocked, Checks failed or pending, Draft, Checking; GitHub works this out on the first ask, so Checking asks again once a few seconds later) and one line for the checks of its head commit, such as "1 failing · 2 pending · 4 passed" (skipped counts as passed; cancelled and those needing an action are told apart from failing). The checks themselves, with logs and reruns, are in Orca's Checks tab: the line opens it for the workspace's pull request, and the pull request's checks on GitHub for any other. The reviewers still asked follow. Its timeline adds reviews (approved, requested changes, reviewed, dismissed) and the merge. The comments a review left on the diff are not shown here: on the workspace's pull request, Open in Checks opens Orca's Checks tab, which shows and answers review threads beside the code; View on GitHub opens them there. From the detail: comment, edit and delete comments, react, edit the title, body, labels and assignees, Review… (Comment, Approve or Request changes, with the comment box's text as the review; only an approval may be empty, and on your own pull request only a comment is offered; while a review is written, Enter and Comment send nothing alone). A mention of an issue or pull request of this repo opens it in its tab.

When the Issues tab shows a workspace, it opens what that workspace showed last there in this panel run (an issue or the list); the first time, the issue Orca links to the workspace (one made from it), or the list when there is none. Back and tab switches stay put. Back reloads the list after a change. Refresh asks for the repo again and reloads the page, issue or pull request on screen, and on the Pull requests tab looks for the branch's pull request again; Open on GitHub opens the tab's page of the repo, or the open row. A state shows as a tinted glyph (Orca tones, so it follows the theme): open green, done and merged in the text colour, not planned, draft, cancelled and skipped grey, closed and failed red, running and waiting amber.

The Actions tab starts on the runs of the focused workspace's branch (every event, newest first; `N runs on <branch>`), with All branches one press away and Only <branch> to come back; a branch filter or `branch:` in the search wins. A run opens with its state, workflow and attempt, what started it, its jobs (each opens its steps with their state and time, View log once the run is done, and Log on GitHub) and, when it failed, its failed steps' logs already open; a failed job whose log gh could not read is named with the reason, beside the others. Logs keep each step's last lines so a whole answer stays under the panel's 256 KiB message limit, say how many lines they show, and link to the full log on GitHub. A run that is done offers Rerun failed jobs and Rerun all jobs, then waits for the new attempt (GitHub starts it a moment later); one still going offers Cancel run (asked first) and is live: the worker reads it every 10 s while it changes, backing off to 60 s while it does not, and posts `run.progress` to the panel; the list row follows. A run waiting for a deployment approval names the environments; for those you may review it offers Approve and Reject (asked first, sent together with GitHub's empty comment), names the ones you may not, and keeps Review deployments on GitHub. A finished run lists its artifacts (name, size, when they expire; expired ones greyed), each opening the run's artifacts on GitHub, where they download. Leaving the run or the Actions tab, or closing the panel, stops it. Run workflow (▶ on the Actions toolbar) opens a form: the workflow (the filtered one, else the first), the branch or tag to read it from and run it on (the workspace's branch when GitHub has it, else the default branch), and its `workflow_dispatch` inputs by type (text, switch, choice, environment). A branch typed in the box is read on Enter, and Run waits for it. After Run, the new run opens once GitHub shows it (a few seconds); else the list says the run was requested. A workflow without that trigger says so; a file the panel cannot read gets name and value rows instead.

## Files

`src/` holds only code that runs in Orca: the entries `src/worker.ts` and `src/panel.tsx`, then `src/shared/` (imported by both sides), `src/worker/` (Node side) and `src/panel/` (panel side), each by feature. Tests sit in `tests/` at the same path as the file they test, with canned answers in `tests/fixtures/`.

- `src/shared/protocol.ts`: the requests `repo.get`, `repo.pick`, `repo.unpick`, `issues.list`, `runs.list`, `labels.list`, `workflows.list`, `assignees.list`, `repo.links`, `issue.get`, `issue.timeline`, `issue.comment`, `comment.edit`, `comment.delete`, `issue.close`, `issue.reopen`, `issue.edit`, `issue.create`, `reaction.set`, `pull.get`, `pull.timeline`, `pull.comment`, `pull.edit`, `pull.review`, `orca.show` (Orca's Tasks page or Checks tab through `commands.run`, which needs `workspace:write`), `run.get`, `run.logs`, `run.rerun`, `run.cancel`, `run.review`, `run.watch`, `workflow.form`, `workflow.run` and the events `repo.changed` and `run.progress`. Every answer is `Answer<T>`: `{ ok: true, ... }` or `{ ok: false, error: { code, message } }`, since a thrown code would reach the panel only as `action_failed`.
- `src/worker/gh.ts`: `runGh(args, { cwd, signal, json, timeoutMs, maxBuffer })` runs `gh` and throws a `GhError` whose `code` the panel can explain. Handlers take it injected, so tests never call real GitHub.
- `src/worker/exec.ts`: `run` (child processes, with the user's PATH first), `terminalPath` (the folder a terminal runs in) and `workspaceLinks` (the issue and pull request Orca links to a workspace, from `orca worktree show --json`; host API has neither), both from the Orca CLI and null on any failure, as its JSON is not part of the plugin contract. The CLI is looked for in the macOS app bundle, then as `orca` on PATH; on Linux and Windows only PATH is tried, so without `orca` on PATH a terminal never breaks a tie and the panel asks for a pick instead.
- `src/worker/repo/focus.ts`: finds the focused workspace's folder. `workspace.readContext` gives only a branch and a name, so it matches them against `workspace.list`, and when that is not one workspace (root clones are named after their branch, so every repo on `main` looks alike) it asks which folder a focused terminal runs in, since that terminal belongs to the focused workspace, and when none tells it uses the folder the person picked (kept in storage under `picks` per branch, name and the set of projects of the matching workspaces (a JSON array of their project ids, or names before host API 1.7), so it is asked again when a clone of another repo joins or leaves that set; used while the folder is still one of the matches, forgotten with Change workspace). Within one set, clones of different repos still share the pick, since `workspace.readContext` does not name the focused workspace's project (stablyai/orca#40492). With neither, the panel lists the candidates to pick from, each as "<project> · <branch>" (with the folder name added when two choices share both, e.g. "app · main (app-2)") and its path under it.
- `src/worker/repo/repo.ts`: `gh repo view --json nameWithOwner,url` in that folder, and the tracker behind `repo.get`: it follows `workspace.changed`, keeps a found repo per folder, asks again after an error, and posts `repo.changed` to open panels when the answer changes.
- `src/worker/lists.ts`: one page per request. Issues go through GitHub's GraphQL search (`repo:o/r is:issue is:open author:… label:… sort:created-desc <words>`), which pages by cursor and, when asked, counts open and closed in the same call. Runs go through the REST `actions/runs` API, paged by number, narrowed to the workspace's branch (`git rev-parse` in its folder) when `scope` is `branch`; it has no word search, so the runs search takes qualifiers only: `branch:`, `status:`, `actor:`, `event:`, `workflow:` (an id, a file name, or a workflow name looked up first; quote a name with spaces). Also the repo's label names and workflows, for the filters.
- `src/worker/timeline.ts`: what issues and pull requests share in the worker: both ends of a timeline in one GraphQL query (`timelineItems` first 30 and last 10), later pages by cursor, each body cut to fit and a page ended early once its comments and reviews fill their share of the 256 KiB message limit.
- `src/worker/issues/issues.ts`: one issue. Reads through GraphQL: the issue with its reactions and its timeline (comments, cross-references, closed and reopened). Writes through gh's issue commands (`gh issue comment`, `close --reason`/`--duplicate-of`, `reopen`, `edit --add-label`…, `create`), which take label and login names; comments are edited and deleted through the REST API by id, reactions through GraphQL `addReaction`/`removeReaction` by node id (the REST API needs the reaction's own id to remove it).
- `src/worker/pulls/pulls.ts`: one pull request. Reads through GraphQL: its refs, `mergeable` and `mergeStateStatus`, `reviewDecision`, review requests, the head commit's `statusCheckRollup` counts by state (`checkRunCountsByState`, `statusContextCountsByState`: every check, however many) and its timeline (comments, reviews, cross-references, closed, reopened, merged). A pending review (the viewer's draft) and the close that a merge makes are left out, and the timeline's size is its `filteredCount`, as `totalCount` ignores `itemTypes` on a pull request. Writes through `gh pr comment`, `edit` and `review --approve|--request-changes|--comment --body`. `branchPull` asks `gh pr view --json number` in the folder for the branch's pull request; `repo.links` answers it when Orca links none and the Pull requests tab asks with `branch` (the Issues tab never does, so it pays no gh call).
- `src/worker/runs/runs.ts`: one run. The run and the jobs and steps of its latest attempt through the REST API; logs of a finished run through `gh run view --job N --log-failed` per failed job (at most 5, as Orca's Checks panel reads; gh reads one job's log in about a second, a whole run's in tens; a job that fails is named, the others still show) or `--log` for one job, with a 60 s limit and a 64 MiB buffer; a run too big for one message drops the steps of passed jobs, then all steps; `gh run rerun [--failed]`, `gh run cancel`; `run.watch`, which holds up to 100 s, reads the run every 10 s while its jobs and steps change and up to every 60 s while they do not, and posts it to the panel that asked until it is done (with `attempt`, until that attempt is) or the panel stops waiting; a waiting run's pending deployments and their approval or rejection (`POST pending_deployments`; gh has no command for it); a finished run's artifacts; and the Run workflow form (`gh workflow view --yaml --ref`, the repo's environments) and `gh workflow run --ref -f name=value`, then a few looks for the run it started.
- `src/worker/runs/logs.ts`: gh's log lines cut into steps, without timestamps, colour codes or group and action markers, and trimmed to the end of each step within one budget.
- `src/worker/runs/workflow-inputs.ts`: the `on:` block of a workflow file read for `workflow_dispatch` and its inputs. The plugin carries no YAML library, so it reads the plain YAML these blocks are written in and gives up (inputs null) on anchors, flow mappings or values over several lines.
- `src/panel/look.ts`: glyph, tone and words for each state, timeline event, reaction and error code.
- `src/panel/refs.ts`: turns `#12` and `owner/repo#12` into Markdown links, leaving code, links and URLs alone.
- `src/panel/store.ts`: the panel's atoms and actions: the selected tab, and per tab the search, open/closed/all, filters, order, counts, a stack of page cursors and the open row; label, workflow and assignee choices.
- `src/panel/thread/thread-store.ts`: an open issue or pull request (a thread), one per tab: its timeline pages, what is being typed, and every write both share; one write at a time, and the thread is asked for again after it, except comment edits, deletes and reactions, which change in place. `src/panel/issues/issue-store.ts` adds closing with a reason and the new issue form, `src/panel/pulls/pull-store.ts` finding the workspace's pull request, the review, the merge-state retry and the hand-offs to Orca.
- `src/panel/runs/run-store.ts`: the open run, its open job and log, its writes and its watch (aborted when the run is left), and the Run workflow form.
- `src/panel/views.tsx`, `src/panel/thread/thread-view.tsx` (posts, reactions, the timeline, metadata lines and pickers), `src/panel/issues/issue-view.tsx`, `src/panel/issues/issue-forms.tsx`, `src/panel/pulls/pull-view.tsx`, `src/panel/runs/run-view.tsx`, `src/panel/parts.tsx`, `src/panel.tsx`: the components.
- `src/panel.check.ts`: `orca plugin check` scenarios, with the worker stubbed: no workspace, several workspaces to pick from, not a GitHub repo, gh logged out, empty repo, rate limited, each tab with rows, runs with one queued; through a workspace linked to issue 120, an issue open, closed, with a long timeline, read only and not found; a branch with no pull request; and through a workspace whose pull request is 131, one with failing checks and reviews, your own, ready to merge, with conflicts, a draft without checks, closed, merged and not found. Scenarios cannot press, so reviews and hand-offs are covered by `tests/panel/pulls/pull-view.test.tsx`.

Error codes: `no_workspace`, `workspace_not_found`, `ambiguous_workspace` (with `candidates`), `remote_workspace`, `host_failed` (Orca failed with no code; with one, `not_allowed`, `host_rate_limited`, `unavailable`, `timeout` or `action_failed`), `not_a_repo`, `gh_missing`, `gh_logged_out`, `not_found`, `rate_limited`, `timeout`, `cancelled`, `bad_query`, `gh_failed`.

## Develop

```sh
orca plugin types .        # typings into .orca/types/, needed before tsc
orca plugin validate .
orca plugin test .         # GH_LIVE=1 also runs tests/worker/repo/repo.test.ts against the real gh
orca plugin check .
npm install && npx tsc -p .
orca plugin dev watch .    # loads this folder into Orca and prints its logs and reloads; Ctrl-C unloads it
orca plugin dev request . issues.list --data '{"state":"open","query":"","after":null}'
```

The plugin id is `gh-focus`. Orca names the publisher after where the plugin is installed from: the
GitHub or GitLab owner of its repository (`chimeyrock999.gh-focus` from the community catalog), or
`local` for a folder. See
https://github.com/stablyai/orca/blob/main/docs/reference/plugin-authoring.md.
