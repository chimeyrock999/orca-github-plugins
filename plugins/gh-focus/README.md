# gh Focus

For GitHub repos: the issue, pull request and Actions runs of the workspace you're in, beside your code. Read, comment, review and rerun without leaving the editor for the Tasks page. Not affiliated with GitHub.

Small and focused on the work at hand: the everyday reading, answering and reviewing happens beside the code. The detail work (merge, reviewers, the files diff, Projects) stays on Orca's Tasks page and pull request page, and the panel hands off to them. The Issues and Pull requests tabs show only what Orca links to the workspace and hand the repo's lists, search and new issues to Orca's Tasks page.

## Features

A right-sidebar panel that follows the focused workspace, with three tabs:

- **Issues**: the issues Orca links to the workspace. One opens by itself, several make a short list. Read the body and timeline; comment, edit or delete comments, react, close (completed, not planned, duplicate) or reopen, edit the title, body, labels and assignees.
- **Pull requests**: the workspace's pull request (linked in Orca, or the branch's). Its review decision, whether it can merge and one line for its checks; comment, react, edit, and review (Comment, Approve, Request changes).
- **Actions**: the runs of the workspace's branch, or every branch, with search and filters. A run's jobs and steps, the failed steps' logs already open, rerun or cancel, approve or reject a waiting deployment, its artifacts, Run workflow with its inputs, and live updates while it runs.
- **Hand-offs to Orca**: Tasks opens Orca's Tasks page (the repo's lists, search, new issues), Open in Checks opens Orca's Checks tab (review threads, check logs). With nothing linked, the panel shows how to link an issue and can ask the workspace's agent to do it.
- **Light on GitHub**: answers are kept in memory for a short while and a write drops what it changes, so the panel spends little of the GitHub budget it shares with Orca, and says so when that budget runs low.

## Requirements

- Orca `1.4.256` or later.
- The [`gh` CLI](https://cli.github.com), logged in (`gh auth login`) with access to the repo. Every GitHub call goes through it; the plugin stores no tokens.
- A workspace whose folder is a clone of a GitHub repo.
- Orca's own CLI, which tells the plugin what Orca links to a workspace. On macOS it ships in the app; on Linux and Windows, put `orca` on PATH. Without it the Issues tab finds no linked issue and the Pull requests tab uses the branch's pull request.

## Install

From the first release on: [Open in Orca](https://orca.dev/plugins/chimeyrock999.gh-focus?catalog=community), or in Orca: Settings → Plugins, community catalog, **gh Focus**. Orca asks you to approve the permissions below; an update that adds one asks again.

## Permissions

gh Focus is a `trusted-worker`: its worker runs `gh` and Orca's CLI on your machine with your user's access.

- `storage:own`: remembers which workspace you picked when Orca cannot tell which one is focused.
- `workspace:read`: the focused workspace's name, branch and terminals, to find its folder and repo.
- `workspace:write`: only to open Orca's Tasks page and Checks tab (`commands.run`); it never opens, creates or renames a workspace.
- `agent:read`: finds a free agent of the workspace for Ask agent.
- `terminal:send`: types the link request into that agent's terminal, without pressing Enter, so you read it and send it.

## Panel

Tabs Issues | Pull requests | Actions. The Issues and Pull requests tabs list nothing repo-wide: only the issues and pull requests Orca links to the focused workspace (one it was made from, one made in Orca, or any linked with `orca reference add`; Orca keeps several per workspace), and on Pull requests, when Orca links none of this repo, the one gh finds for the branch. With exactly one, the tab opens it. With several, it shows a short list (state glyph, title, `#N by <author> · updated …`, newest activity first; one of another repo carries an `owner/name` badge) and opens none by itself; an item of another repo opens in the panel like any other and is read and written in its own repo (`#12` in its text, its labels and assignees, its mentions are that repo's; gh's issue and pr commands get `-R owner/name`; an item on another host, such as a GitHub Enterprise one while the repo is on github.com, is left out, as its `owner/name` would name another repo here), except that only the focused repo's pull request hands its checks to Orca's Checks tab; one opened from the list has ← Back to linked issues (or pull requests). With none, it says so and shows how to link one: the `orca reference add <repo url>/issues/<number> --worktree current` command for this repo, and Ask <agent> to link, which types that request into the workspace's free agent (one waiting or done, never one at work, whose terminal runs in this workspace's folder) without pressing Enter, so you read it and send it; with no free agent there is only the command. Tasks (on the empty state, and as "← Tasks" on the top row of the list and of every detail, with the detail's Edit and Open on GitHub beside it and any Back below) opens Orca's Tasks page, which lists, searches and filters the repo and makes new issues; Orca's command takes no repo, so the page opens with its own repo selection.

The Actions tab has a list with its own search, filters, page and open row. It takes the panel's height and shows GitHub's page of 30 runs, with Previous / Next pinned under it; the runs list stops at 1,000 results once a filter is set, and the page line says so. The filter button opens workflow, status, event and branch and shows how many are on.

An issue opens as GitHub shows it: state, labels, assignees and milestone, the body, then its timeline of comments, "mentioned this" (another issue or pull request that links here: an issue of this repo opens in the panel, anything else on GitHub) and closed or reopened events. A long timeline shows its first 30 and latest 10 items with Load more between. `#12` and `owner/repo#12` in text are links; images only show on GitHub (panel Markdown loads no remote images), and text past the panel's message limit is cut with a link to the rest. From the detail: comment (Cmd+Enter), edit or delete any comment GitHub lets you, close as completed, not planned or a duplicate (asked first; with text in the box it is Close with comment), reopen, edit the title and body, pick labels and assignees, and react (the ☺ + strip offers GitHub's eight).

On the Pull requests tab, the branch's pull request (one opened with `gh pr create` or on GitHub) stands in when Orca links none of this repo. Orca's own pull request views close, reopen and merge. A pull request opened from a mention has ← Back to the workspace's only one, or to the list. It reads like an issue, with what only it has: `base ← head` (`owner:branch` from a fork), and in Orca's own words and counting, so it reads like Orca's Checks tab: its review decision (Approved, Changes requested, Approval required; no line when none is needed), whether it can merge (Able to merge, Conflicts, Behind, Blocked, Checks failed or pending, Draft, Checking; GitHub works this out on the first ask, so Checking asks again once a few seconds later) and one line for the checks of its head commit, such as "1 failing · 2 pending · 4 passed" (skipped counts as passed; cancelled and those needing an action are told apart from failing). The checks themselves, with logs and reruns, are in Orca's Checks tab: the line opens it for the workspace's pull request (the first linked one of this repo, or the branch's), and the pull request's checks on GitHub for any other. The reviewers still asked follow. Its timeline adds reviews (approved, requested changes, reviewed, dismissed) and the merge. The comments a review left on the diff are not shown here: on the workspace's pull request, Open in Checks opens Orca's Checks tab, which shows and answers review threads beside the code; View on GitHub opens them there. From the detail: comment, edit and delete comments, react, edit the title, body, labels and assignees, Review… (Comment, Approve or Request changes, with the comment box's text as the review; only an approval may be empty, and on your own pull request only a comment is offered; while a review is written, Enter and Comment send nothing alone). A mention of an issue or pull request of this repo opens it in its tab.

Each time a tab shows a workspace, it starts from what Orca links to it, not from what it showed before. Tab switches stay put. Back reloads the list after a change. Refresh asks for the repo and what is linked again (and on Pull requests for the branch's pull request; the other tab asks again when it next shows), so an item linked meanwhile opens, and reloads the runs page, issue or pull request on screen; Open on GitHub opens the tab's page of the repo, or the open row. A state shows as a tinted glyph (Orca tones, so it follows the theme): open green, done and merged in the text colour, not planned, draft, cancelled and skipped grey, closed and failed red, running and waiting amber.

The Actions tab starts on the runs of the focused workspace's branch (every event, newest first; `N runs on <branch>`), with All branches one press away and Only <branch> to come back; a branch filter or `branch:` in the search wins. A run opens with its state, workflow and attempt, what started it, its jobs (each opens its steps with their state and time, View log once the run is done, and Log on GitHub) and, when it failed, its failed steps' logs already open; a failed job whose log gh could not read is named with the reason, beside the others. Logs keep each step's last lines so a whole answer stays under the panel's 256 KiB message limit, say how many lines they show, and link to the full log on GitHub. A run that is done offers Rerun failed jobs and Rerun all jobs, then waits for the new attempt (GitHub starts it a moment later); one still going offers Cancel run (asked first) and is live: the worker reads it every 10 s while it changes, backing off to 60 s while it does not, and posts `run.progress` to the panel; the list row follows. A run waiting for a deployment approval names the environments; for those you may review it offers Approve and Reject (asked first, sent together with GitHub's empty comment), names the ones you may not, and keeps Review deployments on GitHub. A finished run lists its artifacts (name, size, when they expire; expired ones greyed), each opening the run's artifacts on GitHub, where they download. Leaving the run or the Actions tab, or closing the panel, stops it. Run workflow (▶ on the Actions toolbar) opens a form: the workflow (the filtered one, else the first), the branch or tag to read it from and run it on (the workspace's branch when GitHub has it, else the default branch), and its `workflow_dispatch` inputs by type (text, switch, choice, environment). A branch typed in the box is read on Enter, and Run waits for it. After Run, the new run opens once GitHub shows it (a few seconds); else the list says the run was requested. A workflow without that trigger says so; a file the panel cannot read gets name and value rows instead.

## Files

A right-sidebar panel with the issues and pull requests linked to the focused workspace and the Actions runs of its repo. Every GitHub call goes through the `gh` CLI already logged in on the machine; the plugin stores no tokens. The panel (`src/panel.tsx`) asks with `plugin.request`, the plugin's own worker (`src/worker.ts`) answers with `orca.panels.handle` and runs `gh`; `src/shared/protocol.ts` types both sides. Orca transpiles both files when they load, so there is no build step: save and the panel or worker reloads.

`src/` holds only code that runs in Orca: the entries `src/worker.ts` and `src/panel.tsx`, then `src/shared/` (imported by both sides), `src/worker/` (Node side) and `src/panel/` (panel side), each by feature. Tests sit in `tests/` at the same path as the file they test, with canned answers in `tests/fixtures/`.

- `src/shared/protocol.ts`: the requests `repo.get`, `repo.pick`, `repo.unpick`, `repo.links`, `items.get`, `agent.find`, `agent.ask` (a free agent of the workspace, and typing the link request into it, through `agents.list` and `terminal.sendText`, which need `agent:read` and `terminal:send`), `runs.list`, `labels.list`, `workflows.list`, `assignees.list`, `issue.get`, `issue.timeline`, `issue.comment`, `comment.edit`, `comment.delete`, `issue.close`, `issue.reopen`, `issue.edit`, `reaction.set`, `pull.get`, `pull.timeline`, `pull.comment`, `pull.edit`, `pull.review`, `orca.show` (Orca's Tasks page or Checks tab through `commands.run`, which needs `workspace:write`), `run.get`, `run.logs`, `run.rerun`, `run.cancel`, `run.review`, `run.watch`, `workflow.form`, `workflow.run`, `cache.drop` (Refresh), `budget.get` and the events `repo.changed`, `run.progress` and `budget.changed`. Every answer is `Answer<T>`: `{ ok: true, ... }` or `{ ok: false, error: { code, message } }`, since a thrown code would reach the panel only as `action_failed`.
- `src/worker/gh.ts`: `runGh(args, { cwd, signal, json, timeoutMs, maxBuffer, partial })` runs `gh` and throws a `GhError` whose `code` the panel can explain; with `partial`, a GraphQL answer whose only errors are NOT_FOUND or FORBIDDEN (another org's SAML, say) keeps its data (gh exits 1 on any error). Handlers take it injected, so tests never call real GitHub.
- `src/worker/cache.ts`: what the worker keeps of GitHub's answers, in memory only: a short TTL for what changes and a long one for labels, assignees and workflows, one gh call for identical reads in flight, and what a write can change dropped after it (Refresh drops everything); REST reads ask with the ETag they have, so an unchanged answer (304) costs no budget. Below a tenth of the REST budget, answers are kept longer, `run.watch` reads slower, and the panel shows GitHub budget low until the budget resets.
- `src/worker/exec.ts`: `run` (child processes, with the user's PATH first), `terminalPath` (the folder a terminal runs in) and `workspaceLinks` (the GitHub issues and pull requests Orca links to a workspace: `linkedItems` in `orca worktree show --json`, the same list `orca reference list` answers, each with the `owner/name` its URL names; plus the one `linkedIssue` and `linkedPR` an older link kept when the list lacks them, as Orca's own reading does; host API has neither), both from the Orca CLI and null on any failure, as its JSON is not part of the plugin contract. The CLI is looked for in the macOS app bundle, then as `orca` on PATH; on Linux and Windows only PATH is tried, so without `orca` on PATH a terminal never breaks a tie and the panel asks for a pick instead.
- `src/worker/repo/focus.ts`: finds the focused workspace's folder. `workspace.readContext` gives only a branch and a name, so it matches them against `workspace.list`, and when that is not one workspace (root clones are named after their branch, so every repo on `main` looks alike) it asks which folder a focused terminal runs in, since that terminal belongs to the focused workspace, and when none tells it uses the folder the person picked (kept in storage under `picks` per branch, name and the set of projects of the matching workspaces (a JSON array of their project ids, or names before host API 1.7), so it is asked again when a clone of another repo joins or leaves that set; used while the folder is still one of the matches, forgotten with Change workspace). Within one set, clones of different repos still share the pick, since `workspace.readContext` does not name the focused workspace's project (stablyai/orca#40492). With neither, the panel lists the candidates to pick from, each as "<project> · <branch>" (with the folder name added when two choices share both, e.g. "app · main (app-2)") and its path under it.
- `src/worker/repo/repo.ts`: `gh repo view --json nameWithOwner,url` in that folder, and the tracker behind `repo.get`: it follows `workspace.changed`, keeps a found repo per folder, asks again after an error, and posts `repo.changed` to open panels when the answer changes.
- `src/worker/linked/linked.ts`: the linked items of the focused repo's workspace (`repo.links`; none when the workspace's project is another repo), their title, state, author and last activity in one GraphQL query (a `repository` block per repo, an `issueOrPullRequest` per number, at most 50, and the list says when there are more; one GitHub has no answer for keeps Orca's title and no state), and the free agent and the prompt for Ask agent (typed only into the agent the panel offered, while it is still free and its terminal is in the workspace's folder).
- `src/worker.ts`: an issue or pull request request with `repo` (`owner/name`) works on that repo instead of the focused one: GraphQL and REST name it, gh's `issue`, `pr` and `label` commands get `-R` (`repoFlag` in `src/worker/lists.ts`), and gh still runs in the workspace folder; a name that is not `owner/name` (`isRepoName` in `src/shared/protocol.ts`: an owner of letters, digits and dashes, a name that is not `.` or `..`) is refused before gh runs, and the link parser never makes one a repo.
- `src/worker/lists.ts`: one page of runs per request. Runs go through the REST `actions/runs` API, paged by number, narrowed to the workspace's branch (`git rev-parse` in its folder) when `scope` is `branch`; it has no word search, so the runs search takes qualifiers only: `branch:`, `status:`, `actor:`, `event:`, `workflow:` (an id, a file name, or a workflow name looked up first; quote a name with spaces). Also the repo's label names (for the label picker) and workflows (for the filter), and the issue and pull request states as GitHub names them.
- `src/worker/timeline.ts`: what issues and pull requests share in the worker: both ends of a timeline in one GraphQL query (`timelineItems` first 30 and last 10), later pages by cursor, each body cut to fit and a page ended early once its comments and reviews fill their share of the 256 KiB message limit.
- `src/worker/issues/issues.ts`: one issue. Reads through GraphQL: the issue with its reactions and its timeline (comments, cross-references, closed and reopened). Writes through gh's issue commands (`gh issue comment`, `close --reason`/`--duplicate-of`, `reopen`, `edit --add-label`…), which take label and login names; comments are edited and deleted through the REST API by id, reactions through GraphQL `addReaction`/`removeReaction` by node id (the REST API needs the reaction's own id to remove it).
- `src/worker/pulls/pulls.ts`: one pull request. Reads through GraphQL: its refs, `mergeable` and `mergeStateStatus`, `reviewDecision`, review requests, the head commit's `statusCheckRollup` counts by state (`checkRunCountsByState`, `statusContextCountsByState`: every check, however many) and its timeline (comments, reviews, cross-references, closed, reopened, merged). A pending review (the viewer's draft) and the close that a merge makes are left out, and the timeline's size is its `filteredCount`, as `totalCount` ignores `itemTypes` on a pull request. Writes through `gh pr comment`, `edit` and `review --approve|--request-changes|--comment --body`. `branchPull` asks `gh pr view --json number` in the folder for the branch's pull request; `repo.links` answers it when Orca links none and the Pull requests tab asks with `branch` (the Issues tab never does, so it pays no gh call).
- `src/worker/runs/runs.ts`: one run. The run and the jobs and steps of its latest attempt through the REST API; logs of a finished run through `gh run view --job N --log-failed` per failed job (at most 5, as Orca's Checks panel reads; gh reads one job's log in about a second, a whole run's in tens; a job that fails is named, the others still show) or `--log` for one job, with a 60 s limit and a 64 MiB buffer; a run too big for one message drops the steps of passed jobs, then all steps; `gh run rerun [--failed]`, `gh run cancel`; `run.watch`, which holds up to 100 s, reads the run every 10 s while its jobs and steps change and up to every 60 s while they do not, and posts it to the panel that asked until it is done (with `attempt`, until that attempt is) or the panel stops waiting; a waiting run's pending deployments and their approval or rejection (`POST pending_deployments`; gh has no command for it); a finished run's artifacts; and the Run workflow form (`gh workflow view --yaml --ref`, the repo's environments) and `gh workflow run --ref -f name=value`, then a few looks for the run it started.
- `src/worker/runs/logs.ts`: gh's log lines cut into steps, without timestamps, colour codes or group and action markers, and trimmed to the end of each step within one budget.
- `src/worker/runs/workflow-inputs.ts`: the `on:` block of a workflow file read for `workflow_dispatch` and its inputs. The plugin carries no YAML library, so it reads the plain YAML these blocks are written in and gives up (inputs null) on anchors, flow mappings or values over several lines.
- `src/shared/look.ts`: glyph, tone and words for each state, timeline event, reaction and error code.
- `src/panel/refs.ts`: turns `#12` and `owner/repo#12` into Markdown links, leaving code, links and URLs alone.
- `src/panel/store.ts`: the panel's atoms and actions: the selected tab, the open row of each tab, and the runs list's search, filters, scope and stack of page cursors; workflow choices, and label and assignee choices kept per repo, so a picker on another repo's item never offers this repo's.
- `src/panel/thread/thread-store.ts`: an open issue or pull request (a thread), one per tab: what Orca links to the workspace and when the tab opens one by itself, the linked list's rows, its timeline pages, what is being typed, and every write both share; one write at a time, and the thread is asked for again after it, except comment edits, deletes and reactions, which change in place. `src/panel/issues/issue-store.ts` adds closing with a reason, `src/panel/pulls/pull-store.ts` the review and the merge-state retry, `src/panel/linked/link-store.ts` the hand-offs to Orca and Ask agent.
- `src/panel/runs/run-store.ts`: the open run, its open job and log, its writes and its watch (aborted when the run is left), and the Run workflow form.
- `src/panel/views.tsx`, `src/panel/thread/thread-view.tsx` (posts, reactions, the timeline, metadata lines and pickers), `src/panel/linked/linked-view.tsx` (the linked list and the empty state), `src/panel/issues/issue-view.tsx`, `src/panel/pulls/pull-view.tsx`, `src/panel/runs/run-view.tsx`, `src/panel/parts.tsx`, `src/panel.tsx`: the components.
- `src/panel.check.ts`: `orca plugin check` scenarios, with the worker stubbed: no workspace, several workspaces to pick from, not a GitHub repo, gh logged out, a repo with no runs, rate limited, runs with rows and with one queued; nothing linked (with and without a free agent), several linked issues (one of another repo) and several pull requests, and a list GitHub will not answer for; through a workspace linked to issue 120 alone, an issue open, closed, with a long timeline, read only and not found; a branch with no pull request; and through a workspace whose only pull request is 131, one with failing checks and reviews, your own, ready to merge, with conflicts, a draft without checks, closed, merged and not found. Scenarios cannot press, so reviews and hand-offs are covered by `tests/panel/pulls/pull-view.test.tsx`.

Error codes: `no_workspace`, `workspace_not_found`, `ambiguous_workspace` (with `candidates`), `remote_workspace`, `host_failed` (Orca failed with no code; with one, `not_allowed`, `host_rate_limited`, `unavailable`, `timeout` or `action_failed`), `not_a_repo`, `gh_missing`, `gh_logged_out`, `not_found`, `rate_limited`, `timeout`, `cancelled`, `bad_query`, `gh_failed`, `no_agent`.

## Develop

```sh
orca plugin types .        # typings into .orca/types/, needed before tsc
orca plugin validate .
orca plugin test .         # GH_LIVE=1 also runs tests/worker/repo/repo.test.ts against the real gh
orca plugin check .
npm install && npx tsc -p .
orca plugin dev watch .    # loads this folder into Orca and prints its logs and reloads; Ctrl-C unloads it
orca plugin dev request . repo.links --data '{"branch":true}'
```

The plugin id is `gh-focus`. Orca names the publisher after where the plugin is installed from: the
GitHub or GitLab owner of its repository (`chimeyrock999.gh-focus` from the community catalog), or
`local` for a folder. See
https://github.com/stablyai/orca/blob/main/docs/reference/plugin-authoring.md.
